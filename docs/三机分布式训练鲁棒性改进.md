# 三机分布式训练鲁棒性改进

## 已发现的主要风险

1. Windows角色队列曾以“本地进程消失”作为 `COMPLETE`，没有确认4090根端完成同一
   Case，可能产生跨Case错位。
2. 根端此前只检查 `Training finished after 100 rounds`，没有同时强制检查99个
   准确率轮次、每轮完整子服务器更新和零ERROR。
3. 失败后重新启动根进程会覆盖 `root.stdout.log`，需要人工归档失败尝试。
4. 三端只依赖复用端口的开关状态判断Case，端口本身不携带Case身份。
5. TCP和资源等待多数没有跨端状态解释，发生故障时可长时间停留在不明确状态。

## 已实现的改进

### 根端控制面

`queue_control.py` 在4090上原子写入并只读发布：

```text
run_id
case
case_index
phase = starting/running/complete/failed/all_complete
completed_count
accuracy_rounds
updated_at
```

控制面使用真实地址 `http://10.112.81.135:60049/state`。SSH仍只用于管理。

### 跨机器Case令牌

第三台和8G队列在启动角色前，必须确认控制面的 `run_id + case + case_index`
完全一致。角色结束后，必须等根端发布同一Case的 `complete` 才能写本地
`COMPLETE`。

本地历史状态若错误地写过 `COMPLETE`，但根端仍处于该Case，队列记录
`REPLAY_STALE_LOCAL_COMPLETE` 并恢复同一Case，不再跳到下一项。

### 严格完成契约

`validate_case_completion.py` 强制要求：

```text
Training finished after 100 rounds：恰好1次
准确率轮次：严格为Round 1–99
聚合更新轮次：严格为Round 1–99
OfficeHome/DomainNet：每轮valid_updates=2/2
MDSent：每轮valid_updates=4/4
ERROR：0
```

结果原子写入 `completion_validation.json`。只有验证通过并成功生成
`accuracy_summary.json` 后，根端才原子创建 `.formal_complete`。

### 自动保留失败尝试

未完成Case重新启动前，根队列按日志SHA-256去重，将旧日志、根配置和状态写入：

```text
<case>/attempts/attempt_YYYYMMDD_HHMMSS/
```

因此恢复不会静默覆盖失败证据。

## 部署原则

这些改动不会重启当前正式训练。正在运行的旧队列进程继续使用启动时加载的脚本；
文件同步后，只有队列下次重启才启用新控制面。

启用顺序必须是：

1. 先更新4090的根队列、控制面和验证器；
2. 确认真实端口60049可从两台Windows访问；
3. 再更新第三台和8G队列；
4. 启动4090根队列；
5. 最后启动第三台和8G队列。

任何一端看不到60049时不得启用新Windows队列，否则应保留旧队列继续当前Case。

## 后续建议

- 增加每个Case的最大无进展时间和自动告警，但不自动跨Case；
- 将三端版本SHA写入控制状态，拒绝不同版本混跑；
- 在Case开始前记录CPU、内存、磁盘和端口快照；
- 在完成归档中加入三端日志哈希；
- QPS压测与正式训练使用独立计划任务和端口范围，禁止同时运行。
